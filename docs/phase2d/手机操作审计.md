# 手机操作审计（Phase 2D 第一步）

审计对象：5b9683e 的现有联机界面；包括391a077的棋盘修复与Phase 3。当前规则、协议、privacy.ts与游戏数据未改。

## 方法与计数口径

Playwright官方iPhone 13设备描述，390×844 CSS像素、触屏、DPR 3，浏览器引擎为Chromium。这不是实体iPhone/Safari的人工可用性研究。17种操作各实际完成一次；准备阶段在独立测试服务器按原规则回放合法命令，再让浏览器以自己的测试座位重连。没有向浏览器注入游戏状态。

计数从已轮到该角色、界面未遮挡开始，到服务器接受命令并关闭本次掷骰/反馈为止；不含加入房间与动画等待时间。“提交动作”与“已查看/继续”分别列数，合计包含全部确认点击。触控操作用Locator.tap；必要的scrollIntoView计为“需要页面滚动”，不伪称实际手指滑动次数。若使用原生下拉，打开与选择确认分开记；本次测量路径没有用房间下拉。道具测量统一先点房间、再点道具；这不是证明全局最少点击次数，木板的4次也仅指该实际路径。

主截图是提交动作前的真实页面，另附实际出现的反馈截图，统一调用scripts/screenshot-check.ts的assertUiShot/pixelStats，检查可见UI像素非空白。它们是操作局部截图，**不作为完整地图11/10房间计数证明**；完整棋盘继续使用assertFullBoardShot。目标热区以CSS像素测量。

## 主要发现

1. 点击少不等于流程顺手：选牌、技能询问、结束行动和搬运都要离开棋盘向下滚动，之后再返回地图。手指在棋盘内拖动还会被用于平移，页面滚动的入口不明显。
2. 放木板提交动作实测4次：点房间、点道具触发放大、再点道具选目标、滚动后选放置路线。技能使用实测2次：点技能、确认使用。两者超出目标。补测后，翻道具、攻击、躲柜、抓取、治疗各还需1次反馈确认；本次搬运需2次（骰子与后续反馈），完整流程合计见表，不能只用提交动作次数判定达标。
3. 多个44px按钮达不到新要求48px；木板流程最小一次目标热区只有20.9px。小图时一次点击可能只是放大，不是交互，反馈含义不稳定。
4. 现有技能全文、事件日志、状态、物品长期占据下方面板，当前动作入口被挤到屏外。很多单次操作本身符合点击上限，但仍需要滚动。
5. 储物柜公共界面继续只显示被占用；本阶段不改变当前隐私策略。

## 冷启动下载量

MB采用十进制1,000,000字节。CDP禁用浏览器缓存，统计首次进入服务器房间并等待图片解码后的HTTP传输字节（包含HTTP开销，不包含WebSocket消息）。

- 构建目录：147,357,869字节，约147.36 MB。这是磁盘体积，不等于一次实际下载。
- 初始房间（1701，尚未翻起始道具）：57,734,958字节，约57.73 MB HTTP下载。
- 不同中局冷进入：约69.95–84.61 MB。原始值在操作审计记录.json。
- 正式版≤8 MB目标当前未达到。样稿使用现有轻量SVG与场景占位，不能据此声称正式插画版已达标。
