# 第一部分：项目总纲（保存为 AGENTS.md）

## 1. 项目定义

- 游戏：Dead by Daylight: The Board Game（Level 99 Games 出品的实体桌游，基础版）
- 不是电子游戏《Dead by Daylight》。电子游戏中存在、但桌游中不存在的机制、道具、技能，一律不得实现。
- 目标：中文界面的多人网页版，朋友之间私人游玩，手机/平板/电脑浏览器均可操作。
- 项目目录：`E:\DBD-BoardGame-Web`
- 用户持有日文基础版实体桌游，可拍照提供资料。

## 2. 已确认的基础信息（来自官方/零售商公开资料）

- 基础版包含：7 名逃生者、6 名杀人鬼、1 张双面地图（2 张地图）。
- 1 名杀人鬼对 2～4 名逃生者；游戏人数 3～5 人。玩家不足 4 名逃生者时如何补足，以规则书为准（待核对）。
- 公开组件清单（以实物与规则书为最终依据）：
  - 逃生者人物板 ×7、杀人鬼人物板 ×6
  - 道具板块（Prop tiles）×44、可破坏墙道具
  - 献祭进度标记 ×12、发电机进度标记 ×25
  - 先手玩家标记 ×1、恶灵（Entity）标记 ×1
  - 血点标记 ×40
  - 捕兽夹标记 ×4、疯狂标记 ×4、幻影标记 ×7
  - 技能检定骰 ×4、危险骰 ×1
  - 伤害环 ×4
  - 逃生者技能卡 ×28、杀人鬼技能卡 ×24
  - 物品卡 ×16、移动卡 ×21

除上述内容外，任何地图名称、角色名称、卡牌效果、数值、回合流程，**在找到依据之前都视为未确认**。

## 3. 最高原则

1. 原版规则高于编程便利。不得修改机制、数值、地图、胜负条件。
2. **不得编造**。缺失的数据一律标记 `CHECK_REQUIRED`，不得用"合理推测"填入正式数据。
3. 每一条规则、每一张卡、每一条地图连线都必须记录来源（见第 4 节）。
4. 规则有歧义或资料互相矛盾时，**不要自行选择**，写入 `docs/RULE_QUESTIONS.md` 并停下来询问用户。用户的裁定记录在 `docs/HOUSE_RULES.md`。
5. 不得用静态页面、假按钮、占位技能冒充已完成功能。
6. 不得伪造测试结果。所有"已完成"必须附实际运行的测试输出。
7. 每次只做当前指令中的 Phase。完成后输出报告并**停止**，等待用户下一条指令。
8. 修改不得破坏已有功能；每次提交前运行全部测试。

## 4. 资料来源与可信度分级

每条数据必须标注来源等级：

| 等级 | 来源 | 用法 |
|---|---|---|
| A | 用户实物照片 / 扫描（日文版） | 最终依据 |
| B | 官方规则书 PDF、Level 99 官网、官方 Kickstarter 页面与更新、官方 FAQ / 勘误 | 可直接采用，与 A 冲突时以 A 为准并报告 |
| C | BoardGameGeek 文件区与规则论坛中的官方人员回答、官方授权的日文 / 中文代理商资料 | 可采用，需标注 |
| D | 玩家整理的资料、评测文章、开箱与教学视频、维基、中文社区（B站、小红书、知乎、贴吧等） | 只能作为线索，必须由 A/B 级确认后才能进入正式数据 |

数据文件中每一项须包含字段：`source_level`、`source_ref`（网址 / 照片文件名 / 规则书页码）、`status`（CONFIRMED / CHECK_REQUIRED / CONFLICT）。

## 5. 语言与翻译

- 界面语言：简体中文。
- 卡牌、技能、角色名：保存日文原文 + 英文原文（如能找到）+ 中文译文三栏。
- 建立 `packages/game-data/glossary.json` 术语对照表（日 / 英 / 中）。
- 中文译文由 Codex 草拟，标记 `translation_status: DRAFT`，**由用户确认后**改为 `APPROVED`。规则引擎只依赖数据 ID 和结构化效果，不依赖译文。

## 6. 技术架构（简化版）

- 单一代码库，单一 Node.js 服务端，局域网和互联网**使用同一个服务器程序**，只是部署位置不同。
- 前端：React + TypeScript + Vite + Tailwind CSS
- 服务端：Node.js + TypeScript + Socket.IO
- 规则引擎：独立包，纯函数 + 状态机，不依赖网络和界面，可单独测试
- 地图：数据驱动的 Graph（房间节点 + 路线边，每条边有 ID、颜色、方向、特殊状态）
- 持久化：SQLite（局域网与云端都先用 SQLite；对局状态快照 + 事件日志）
- 随机数：只在服务端生成，支持固定种子以便测试复现
- 测试：Vitest（规则引擎）、Playwright（多浏览器联机）

目录结构：

```
apps/web               前端
apps/server            服务端
packages/game-engine   规则引擎
packages/game-data     地图、角色、卡牌、术语数据
packages/shared        共享类型
reference/             原始资料（不得上传到公开仓库）
  rulebooks/ maps/ characters/ perks/ items/ props/ photos/
docs/                  规则矩阵、问题清单、报告
tests/
```

## 7. 联机要求

- 房主创建私人房间，其他人通过房间号、邀请链接或二维码加入，无需安装 App。
- 支持一个玩家账号同时操控多名逃生者（人数不足 4 名逃生者时使用，具体以规则书为准）。
- 隐藏信息（如秘密选择的移动路线、手牌等）只保存在服务端，只发送给有权看到的玩家；不得通过浏览器开发者工具或网络请求看到他人隐藏信息。
- 刷新或断线后可按玩家身份恢复。
- 防止重复提交同一行动。
- 局域网模式：Windows 一键启动脚本，显示本机局域网地址与二维码，断网也能运行（所有字体和素材本地提供）。
- 互联网模式：同一服务器部署到云端（如 VPS / Render / Fly.io 等），支持 HTTPS / WSS。

## 8. 版权

- 本项目仅供私人游玩。`reference/` 中的原版扫描、照片不得提交到公开仓库；Git 仓库必须为私有，并在 `.gitignore` 中排除原版图片素材。
- 原版美术只在本地/私人部署中使用；公开发布前必须另行确认授权。

# 第二部分：Phase 0 执行指令（现在发给 Codex）

请阅读 `AGENTS.md`（即项目总纲），然后执行 Phase 0。**本阶段不写游戏功能代码。**

## 步骤 1：准备目录

- 检查 `E:\DBD-BoardGame-Web` 是否存在，不存在则创建，并建立总纲第 6 节中的目录结构。
- 初始化私有 Git 仓库，配置 `.gitignore`（排除 `reference/` 中的图片与 PDF、`node_modules`、数据库文件）。
- 如果当前 Codex 环境已配置 `$workflow-router` 等工作流 Skill，先按现有工作流进行任务分类和规划。
- 检查 `reference/` 中用户已放入的资料，全部登记。

## 步骤 2：中、英、日三语资料搜索

在要求用户拍照之前，先尽可能从网络找到公开资料。对每个搜索目标都要实际搜索，并记录"找到了什么 / 没找到"。

**英文**
- Level 99 Games 官网与官方商店中的规则书 PDF、FAQ、勘误
- Kickstarter 项目页面与全部 Updates（常含规则说明、卡牌预览、地图预览）
- BoardGameGeek 条目：Files（规则书、卡牌列表、参考卡）、Rules 论坛（特别是设计师 / 官方人员的回答）
- 官方或权威的 How to Play 视频（只作线索，记录时间点）

**日文**
- 日文版发行商 / 代理商的官方页面与规则书下载
- 日本桌游网站与评测（如桌游专门店的商品页、个人桌游博客）
- 日文 BGG 页面、日文玩家的规则问答

**中文**
- 是否存在官方中文版或中文代理；如有，获取官方规则书
- B站、小红书、知乎、贴吧、桌游相关网站上的规则介绍与卡牌翻译（D 级线索）

对每项找到的资料：保存网址、标注可信度等级、摘要内容覆盖了哪些部分（规则 / 地图 / 某些卡牌）。可公开下载的官方规则书可以保存到 `reference/rulebooks/`。

## 步骤 3：建立以下文件

- `docs/SOURCE_MANIFEST.json`：全部资料来源清单（网址或文件、语言、等级、覆盖范围）
- `docs/SEARCH_LOG.md`：每个搜索目标的搜索结果，包括没找到的
- `docs/RULE_MATRIX.md`：按规则书章节拆分的规则条目（准备、回合流程、移动、道具、检定、攻击、挂钩、献祭、胜负等），每条注明来源与状态
- `packages/game-data/MAP_DATA.json`：两张地图的房间与连线（未确认部分留空并标记）
- `packages/game-data/CHARACTER_DATA.json`：13 名角色
- `packages/game-data/PERK_DATA.json`：28 + 24 张技能卡
- `packages/game-data/ITEM_DATA.json`：16 张物品卡
- `packages/game-data/PROP_DATA.json`：44 个道具板块的种类与数量
- `packages/game-data/MOVEMENT_CARD_DATA.json`：21 张移动卡
- `packages/game-data/glossary.json`：日 / 英 / 中术语对照
- `docs/RULE_QUESTIONS.md`：发现的规则歧义与资料冲突
- `docs/MISSING_RESOURCES.md`：缺失资料清单

所有数量必须与总纲第 2 节的组件清单核对；不一致时写入 CONFLICT。

## 步骤 4：输出补充资料请求（给用户的拍照清单）

在 `docs/MISSING_RESOURCES.md` 中，按优先级列出仍需要用户提供的照片，并写清楚拍摄要求：

1. 规则书中网上找不到的页面（写明页码或章节）
2. 两张地图的完整照片（俯拍、整张清晰、再分区域特写，确保路线颜色和箭头可辨认）
3. 网上找不到原文的卡牌（列出具体卡名或编号）
4. 人物板正反面
5. 骰子各面

对已经从 A/B 级来源找到的内容，**不要要求用户重复拍照**。

## 步骤 5：Phase 0 报告并停止

输出简短报告：

- 找到的资料总览（按语言和等级）
- 各数据文件的完成度（已确认数 / 总数）
- 最需要用户提供的前 10 项资料
- `RULE_QUESTIONS.md` 中需要用户裁定的问题
- 对 Phase 1 的架构计划（简要）

然后**停止**，等待用户提供资料或发出下一条指令。

# 第三部分：后续各阶段指令（逐个发送）

每个阶段开头都发送："请阅读 AGENTS.md，执行 Phase X。完成后输出报告并停止。"

### Phase 1：规则引擎（无界面）
- 依据 RULE_MATRIX 中 CONFIRMED 的规则，实现完整状态机：游戏准备、计划、行动、回合结束、胜负判定。
- 地图移动基于 Graph 数据，合法路线由引擎计算。
- 各种检定分别按规则处理，不得把所有结果统一处理。
- 同一轮多个技能的触发与结算顺序严格按规则书。
- **完成标准**：用固定随机种子，以脚本模拟玩家跑完至少 3 局完整对局（逃生者胜、杀人鬼胜各至少 1 局），输出事件日志；全部测试通过。CHECK_REQUIRED 的规则在引擎中明确报错，不得默默跳过。

### Phase 2：数字棋盘与单机界面
- 地图以数据渲染（不是一张背景图），房间、路线、道具可点击。
- 选择移动后高亮合法路线；手机端支持双指缩放、拖动、防误触。
- 下方面板：当前角色、移动卡、技能、物品、血点、状态、操作按钮。
- **完成标准**：在同一台电脑上用"热座模式"手动玩完一局。

### Phase 3：局域网联机
- 房间系统、二维码、断线重连、隐藏信息隔离、一人操控多名逃生者。
- Windows 一键启动脚本。
- **完成标准**：Playwright 用 5 个浏览器窗口跑完一局；另写一个测试，证明一名玩家无法通过网络消息得到他人隐藏信息。

### Phase 4：全部角色、技能卡、物品卡
- 逐张实现，每张卡至少一个单元测试，测试中引用规则来源。
- **完成标准**：全部卡牌状态为 IMPLEMENTED + TESTED，或明确列为 CHECK_REQUIRED 并说明缺什么。

### Phase 5：互联网部署
- 写出中文部署说明（一步一步，面向没有编程经验的用户）。
- **完成标准**：部署后，用不同网络（如手机 4G/5G）的设备加入并完成一局。

### Phase 6：美术与体验
- 深色恐怖风格、骰子动画、音效、移动端优化。不得改变任何规则。

### Phase 7：最终验收
- 输出：规则审计报告、测试报告、未完成事项（CHECK_REQUIRED）报告、中文操作说明、局域网与互联网使用说明。
